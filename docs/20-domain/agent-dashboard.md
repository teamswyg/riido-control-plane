# 에이전트 작업 현황

RIID-5830은 설정 목록의 에이전트 이름에서 현재 실행, 대기열, 실행 기록과 최근 6개월 활동을 조회한다.
업무 상태 변경, 알림 발송과 기기 제어는 이 조회의 책임이 아니다.

## 조회 계약

- `GET /v2/client/workspaces/{workspace_id}/ai-agent/agents/{agent_id}/dashboard?page=1`
  (v1 호환 경로도 제공). 페이지는 1부터 시작하고 한 페이지는 10건이다.
- 배정 하나를 실행 한 건으로 센다. 동일 업무 재배정·재실행은 각각 별도 기록이다.
  실행 완료를 업무 완료로 해석하지 않는다. 같은 배정의 중복 완료 이벤트는 한 건이다.
- 잔디는 서울 시간 기준 이번 달과 앞선 5개월의 일별 완료 실행 수다.
- 큐 진입은 assignment 생성 시각, 실행 시작은 최초 running 이벤트,
  종료는 최초 terminal 이벤트다. 소요 시간은 답변·승인 대기를 포함하고 큐 대기는 제외한다.
  실행 시작을 확인할 수 없는 과거 기록은 소요 시간을 제공하지 않는다.
- 큐 순서는 AssignmentQueueReader를 따르고 현재 실행은 active lease를 재사용한다.
  답변·승인 대기는 공통 confirmation_reason 계약을 소비한다.
- 에이전트 가시성 검사 후 각 업무의 읽기 권한과 요청자 자격증명으로 얻은 메타데이터를 확인한다.
  접근 가능한 업무만 목록·페이지·합계에 포함한다. 권한 서비스 장애는 조회 실패다.
  접근 불가·삭제 업무는 제외한다. 클라이언트 캐시는 계정·워크스페이스·에이전트·페이지로 구분한다.

## 보관과 호환성

기존 assignment operation journal과 assignment snapshot을 원본으로 사용한다.
클라이언트 thread 50개·replay 200개 제한은 집계에 영향을 주지 않는다.
별도 집계 카운터를 쓰지 않으므로 재시작과 이벤트 재전송으로 완료 수가 증가하지 않는다.
남아 있는 원본에서만 이력을 복원하며 `observed_since`는 가장 오래된 접근 가능한 기록이다.
그 이전 이력의 완전성을 보장하지 않는다. 영속 저장소 없는 개발 환경은 세션 기록임을 표시한다.

현재 조회는 기존 저널의 모든 페이지를 읽고 agent별 조회 모델을 구성한다.
업무 권한·메타데이터도 요청마다 확인하므로 이력이 커질수록 비용과 지연이 증가한다.
대규모 운영 전에 agent별 저널 인덱스 및 일괄 업무 권한 조회가 필요하다.
이 변경에는 운영 데이터 보충, 새 인프라와 배포가 포함되지 않는다.
읽기 전용 기능이므로 기존 경로로 되돌려도 저장 이력의 마이그레이션이나 삭제가 필요하지 않다.

## 검증

- 동일 작업의 `riido-contracts`를 Go workspace로 연결한 `go test ./...`: HTTP 권한·오류, 큐→실행→확인→재개→완료, 파일 재시작,
  60회 실행·중복 재생·서울 날짜 경계·페이지·계약 생성 검증.
- client-v2의 `agent-dashboard-dialog.test.tsx`: 로딩·실패·재시도·업무 클릭·표 페이지 이동.
- client-v2의 `e2e/agent-dashboard.spec.ts`: 실제 설정 Route와 MBSW 모달의 브라우저 동작.
  E2E 데이터는 로컬 응답 대체이며 운영 서버 검증으로 해석하지 않는다.
